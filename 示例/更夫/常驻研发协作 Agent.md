## 1. 背景与问题

- 现有 Coding Agent 以单 Session 为单位：多任务并行时人要手动切换、搬运上下文，一个人通常只能同时跟进 3~5 个活跃会话；**单任务上限取决于模型能力，多任务上限取决于人的注意力**。
- 个人开发者的真实痛点：白天上班，晚上才有时间处理自己项目的 Issue、CI 红灯、评审意见；大量"复现→定位→小修→提 PR"级别的事务占用了本可用于决策和创作的时间。
- DeepSeek Harness 团队已验证 Router/Worker 双层 + 事件驱动 + 持久化任务这套架构可行（合成负载下 p95 完成时间 15.7 分钟 vs 单会话 29.5 分钟），但其开源原型明确是研究代码、不可直接生产使用。

**结论**：借鉴其架构思想自研一个轻量、可控、属于自己的常驻 Agent，而非直接使用原型。

## 2. 产品定位与目标

**一句话定位**：一个 7×24 常驻的"数字更夫"——盯着指定 GitHub 仓库，白名单用户提需求它就开工单、独立干活、提 PR 交付；其余时间安静观察、只记录不动手；人只负责决策与验收。

**目标用户**：

- 首要：项目 AI 本人（个人开发者，1 人）；
- 次要（v1.x）：2~5 人小团队 / 外包协作项目的维护者。

**北极星指标**：每周由 Agent 完成、且通过人工验收（PR 被合并）的任务数。

**护栏指标**（任一恶化即回退 observe）：

| 指标                         | 目标             |
| -------------------------- | -------------- |
| 误触发率（噪音消息建单）               | 0              |
| 误接受率（observe 审计中"本不该接"的评估） | ≤ 5%           |
| 单任务平均模型成本                  | ≤ $0.5（窄规则修复类） |
| 人工介入次数 / 任务（验收除外）          | ≤ 1            |

## 3. 范围与非目标

**v1.0 范围**：单 GitHub 仓库 + Web 面板；显式请求执行 + 候选事件 observe 审计；任务持久化与中断恢复；PR 交付（永不自动合并）。

**明确非目标（v1.0 不做，防止范围蔓延）**：

- ❌ 多仓库 / 多实例 / A2A 协作
- ❌ IM 接入（飞书/企微 → v1.1）
- ❌ 常驻 Router 会话与跨信道全局记忆（v1.0 用无状态 Eval，v1.1 引入）
- ❌ 云端存算分离、BYOM 端侧 daemon（v2.0 方向）
- ❌ 投机执行（后台抢跑）
- ❌ 自动合并、生产环境操作、跨月长程记忆

## 5. 产品形态与核心概念

**触点**：① GitHub（Issue/PR 评论、CI 状态）＝ 主要交互面；② Web 面板（本机 `127.0.0.1`）＝ 管理与审计面。产品原则沿用原型哲学："尽可能少占用人的注意力，尽可能多给出价值"——只在需要决策/验收时说话。

**用户可见概念**：工单（Ticket）、阶段（排队/执行中/等事件/待审核/受阻/失败）、决策记录。  
**系统内部概念**（用户无感知）：Trigger / Thread / Assignment / Authorization / Report / Slot / Outbox——定义见 §8 与配套技术蓝图。

## 7. 关键流程（产品级）

1. **显式请求**：白名单用户 Issue 评论 @Agent → 准入=explicit → 建单+授权+订阅 → Worker 独立目录执行 → 提 PR + 原 Issue 回复 → 待审核 → 人工合并 → 工单 ended(merged)。
2. **候选事件（observe）**：CI 红灯 → 准入=candidate → Eval 按规则判断 → 命中则记 would_accept（不动代码）→ 面板审计 → 维护者若认可，发显式请求转流程 1。
3. **评审跟进**：PR 新评论 → 命中订阅 → 直通原工单（不重新评估）→ Worker 补充修改 → 再次 ready；工单结束需满足"关联 PR 全关闭且无未完成后续"。
4. **中断恢复**：进程崩溃 → 重启 → 结束旧执行绑定（保留工单与授权）→ 新 Worker 收到恢复说明 + 补投输入 → 续跑。

## 8. 状态与规则（摘要）

- **Ticket**：`open ⇄ ended`；阶段为**推导值**，优先级：输入未交付 > Blocked/Failed > 待审核 > 等事件 > 执行中 > 排队（规则细节见技术蓝图 §3，与原型语义一致）。
- **Assignment**：`pending → running → ended`；一个工单可先后多个 Assignment。
- **报告**：六类；阶段判定不得只信单个报告，须结合 Assignment 状态、未交付输入、人工等待条件。

## 9. 非功能需求（NFR）

| 类别  | 指标                                                 |
| --- | -------------------------------------------------- |
| 延迟  | webhook 到达→建单 ≤10s；显式请求→首次回应 ≤60s；直通事件→Worker ≤10s |
| 并发  | 默认 2 Worker Slot，可配置；评估按 Thread 串行                 |
| 可用性 | 单机 7×24；重启恢复 ≤60s；轮询兜底容忍 webhook 丢失                |
| 成本  | 见 FR-12 三级预算；Eval/Router 用轻量模型、Worker 用强模型分档       |
| 可观测 | 每事件全链路 trace_id；决策审计可导出 JSON；成本按票统计                |
| 数据  | 全部状态本地 SQLite（WAL），预留 Store 接口以便迁 Postgres         |

## 10. 安全与权限（发布门槛，非可选项）

1. Agent 用**独立 GitHub 账号** + 独立系统用户/容器运行；仓库开分支保护（必须 PR + 独立审批 + CI），Agent 无 bypass、**无 merge 权限**。
2. 凭据经环境/代理注入，**绝不进入模型上下文**；日志脱敏。
3. 外部事件内容在提示词中标记为"数据非指令"；高危操作（merge、删除、对外支付类）硬编码为人工确认。
4. 白名单初始只含 AI 本人；`auto` 模式开启前置条件：observe 审计 ≥2 周且误接受率 ≤5%，且仅限窄规则。
5. 明确接受的原型级风险告知：LLM 处理仓库代码意味着代码出境到模型 API，敏感项目需先评估数据边界。
