## 一、四层架构总览

本轮将演示代码整理为自顶向下的四层，依赖**只能从上层指向下层**，禁止反向依赖。

```text
┌──────────────────────────────────────────────────────────────────┐
│ L4 接入层 / Interface                                            │
│   接入层/入口.道 —— 流程编排、四类演示、全局对象、组装与打印     │
├──────────────────────────────────────────────────────────────────┤
│ L3 应用层 / Application                                          │
│   应用层/评估.道  应用层/执行.道  应用层/恢复.道                 │
│   应用层/准入.道  应用层/授权.道  应用层/调度.道                 │
│   （业务规则与流程；可调用 L1 基础设施层与 L2 领域层）           │
├──────────────────────────────────────────────────────────────────┤
│ L2 领域层 / Domain                                               │
│   领域层/领域.道 —— 工单/触发/决策/报告/授权/话题/阶段推导       │
│   （纯数据结构与规则，不得依赖任何外部模块或 LLM）               │
├──────────────────────────────────────────────────────────────────┤
│ L1 基础设施层 / Infrastructure                                   │
│   基础设施层/存储.道（SQLite）   基础设施层/看板.道（HTTP 呈现） │
│   基础设施层/语言模型.道（LLM 适配器，新增）                     │
│   标准库：数据库 / 密码 / 调度 / 网络 / 编码 / 大模型            │
└──────────────────────────────────────────────────────────────────┘
```


依赖方向自上而下：

```text
L4 接入层/入口.道 ──调用──▶ L3 各业务模块 ──调用──▶ L2 领域层/领域.道
                         │
                         └──调用──▶ L1 基础设施层/语言模型.道 ──▶ 大模型标准库 ──▶ ollama
                         └──调用──▶ L1 基础设施层/存储.道 / 看板.道 ──▶ 数据库 / 网络标准库
                         └──调用──▶ L1 语言模型.工具对话() ──▶ 大模型标准库.工具对话 ──▶ ollama tools
```

- L4 可调用 L3 / L2 / L1；L3 可调用 L2 / L1；L2 只依赖自身；L1 各模块互不依赖（除标准库）。
- 第三轮更新：L1 `基础设施层/语言模型.道` 新增 `.支持工具()` 与 `.工具对话()`，把「大模型」标准库的 `工具定义`／`工具对话`／`工具结果` 接到 Worker 上；详见第七节。
- `领域层/领域.道` 是只读共享契约，本轮任何模块都不得修改。

## 二、逐层职责、模块与依赖方向

### L4 接入层 / Interface

- **职责**：流程编排与演示驱动——组装全局对象、依次跑四类演示、组装看板与打印摘要。它不实现业务规则，只决定"按什么顺序调哪些能力"。
- **包含模块**：`接入层/入口.道`。
- **依赖方向**：向下依赖 L3（评估、执行、准入、授权、调度、恢复）、L2（领域常量与工单/触发/话题构造）、L1（看板）。
- **本轮变化**：创建评估器与执行工单时新增可选的语言模型入参，把本地 LLM 注入业务层；不直接 `从 大模型 导入`。

### L3 应用层 / Application

- **职责**：承载业务规则与流程——准入判定、语义评估、不可变授权、Slot 调度与成本熔断、Worker 执行与报告、崩溃恢复。LLM 只在这一层按需调用，且必须经由 L1 适配器。
- **包含模块**：`应用层/评估.道`、`应用层/执行.道`、`应用层/恢复.道`、`应用层/准入.道`、`应用层/授权.道`、`应用层/调度.道`。
- **依赖方向**：向下依赖 L2 的领域类型与常量，并可调用 L1 的存储、适配器与标准库；**不感知具体模型或 HTTP 细节**。
- **本轮变化**：
  - 评估器优先请 LLM 做语义判断（理由前缀「LLM语义判断：」），失败或不可用时退回关键词规则（前缀「关键词规则：」）。
  - 执行器在生成末报告前最多调用 1 次 LLM 产出中文结论，失败退回模板报告。
  - 模型生成的 token 计入预算，纳入既有的成本熔断。
  - 第三轮：`执行工单` 增加可选 `工具列表`／`工具回调`，用工具调用驱动末报告结论；成功时附工具调用记录与用量，失败退回模板。

### L2 领域层 / Domain

- **职责**：保存纯数据结构与不依赖外部世界的规则——工单、触发、决策、报告、授权、话题、执行绑定，以及阶段推导与重开规则。
- **包含模块**：`领域层/领域.道`（唯一文件）。
- **依赖方向**：只依赖自身与标准库 `密码`（用于去重键哈希），**不得依赖任何外部模块、L1/L3/L4 或 LLM**。
- **约束**：本轮为只读共享契约，所有新能力都通过上层注入，领域对象不新增模型相关字段。

### L1 基础设施层 / Infrastructure

- **职责**：提供与外界的通用能力——持久化、HTTP 呈现、LLM 适配与标准库封装。各模块彼此独立，可单独替换。
- **包含模块**：
  - `基础设施层/存储.道`：SQLite 持久化与幂等（WAL、工单/触发/报告/决策/授权存取、Outbox）。
  - `基础设施层/看板.道`：手写 UTF-8 文本 HTML，按阶段分组展示工单、决策审计流、全局暂停路由；首页标注 LLM 模式，审计页原样转义输出带来源前缀的理由。
  - `基础设施层/语言模型.道`（第二轮新增，第三轮扩展）：封装 `大模型` 标准库，提供 `.可用()` / `.对话()` / `.判断()`，第三轮新增 `.支持工具()` / `.工具对话()`，统一处理环境变量、惰性探测、JSON 提取、工具多轮循环与失败降级。
  - 标准库：`数据库` / `密码` / `调度` / `网络` / `编码` / `大模型`。
- **依赖方向**：只依赖标准库，不依赖上层；通过回调/参数被 L3/L4 使用。
- **约束**：适配器模块级只做定义，**不在导入时发起任何网络请求**；探测惰性执行并缓存。

## 三、LLM 数据流

一次语义判断或 Worker 生成的调用链如下（依赖逐层向下，业务层不直接碰模型 SDK）：

```text
接入层/入口.道
  └─ 创建评估器(规则, 策略版本, 语言模型) / 执行工单(..., 语言模型)
        └─ L3：评估器.评估() / 执行工单()
              └─ L1：基础设施层/语言模型.道
                    .可用()  惰性探测（列出模型，结果缓存）
                    .判断()  语义判断：提取 JSON 结论与理由
                    .对话()  文本生成：Worker 执行结论
                          └─ 从 大模型 导入 创建客户端/消息/对话/列出模型
                                └─ ollama 服务（OLLAMA_HOST，默认 http://localhost:11434）
                                      └─ gemma4:e4b（OLLAMA_MODEL）
```

- 构造函数把语言模型对象**注入**评估器与执行器，L3 只声明"需要语义能力"，不关心来自 ollama 还是其它提供者。
- 配置由 L1 适配器读取：`OLLAMA_HOST` 默认 `http://localhost:11434`，`OLLAMA_MODEL` 默认 `gemma4:e4b`，超时默认 120 秒。
- 评估结果经 `决策.描述()` 进入存储与审计页；理由中的「LLM语义判断：」/「关键词规则：」前缀供看板区分来源。
- 第三轮工具链在 `.对话()` 之外多一条分支：`.工具对话()` → 标准库 `工具对话` → Provider `chat_with_tools` → 归一化 `tool_calls` → 回调执行 → `tool` 消息回填 → 下一轮，详见第七节。

## 四、降级策略与成本记账

降级的核心是：**LLM 是增强项而非依赖**——任何环节失败，演示都继续跑完，只是退回上一轮的关键词/模板能力。

| 场景 | 触发条件 | 降级行为 |
| --- | --- | --- |
| 模型不可用 | 语言模型为空，或 `.可用()` 探测为假（ollama 未启动 / 无模型） | 评估走关键词规则；Worker 末报告走模板文本 |
| 语义判断失败 | `.判断()` 失败、JSON 解析失败或结论非 `would_accept`/`would_ignore` | 评估静默退回关键词规则，理由前缀改「关键词规则：」 |
| 文本生成失败 | `.对话()` 返回失败 | 末报告消息退回模板文本，数据标记 `{"模型来源":"降级"}` |
| 工具调用不可用（第三轮） | `.支持工具()` 为假，或 `工具对话` 返回「成功":假」（后端不支持／调用失败／达到轮次上限） | 末报告退回模板文本；已完成的工具调用记录与累计用量随失败字典带回 |
| 工具回调失败（第三轮） | 回调自身抛异常 | 转成「工具执行失败：...」结果文本回填，不中断演示 |
| 执行模式关闭 | 模式为 `off` | 不调模型，直接 `would_ignore`（原逻辑不变） |

**成本记账**：模型调用成功时，把返回的生成 token 计入工单预算——`预算.记账(单.编号, 0, 生成token数)`；调用数在槽位占用阶段已记过 1，此处只加 token，不重复加调用数。非工具路径每个工单最多调用 1 次 LLM（不在步骤循环里逐条调用），以避免演示过慢并确保成本可控，沿用 FR-12 的成本熔断。第三轮工具驱动模式允许工具对话多轮（默认上限 5 轮），各轮用量累计后一次性计入预算。成功时末报告数据附 `{"模型来源":"ollama", "生成token": n}`，工具模式另附 `{"工具调用记录": [...]}`，便于审计与统计。

## 六、边界与约束

1. L2 不得依赖外部模块或 LLM；LLM 只在 L3 经 L1 适配器调用，业务层不得直接 `从 大模型 导入`；适配器惰性探测并缓存结果，模块级不发起网络请求。
3. LLM 失败一律静默降级，不能让演示中断；`.判断()` 仅接受 `would_accept` / `would_ignore` 两种结论。
4. 看板只渲染 HTML，不改领域对象；审计页原样转义输出理由前缀，据此区分来源。
5. 所有标识符、注释与用户可见消息用中文；核心导出签名保持向后兼容。

## 七、工具驱动执行（第三轮）

第二轮里 Worker 只让模型「写一句话」；第三轮把接口层预留的 `chat_with_tools` 补全为完整协议，并把工具作为「能力」注入 Worker——模型在需要时点名调用工具，结果回填后继续，直到给出结论或达到轮次上限。**领域层 `领域层/领域.道` 未改动**，新能力全部通过可选参数注入。

### 7.1 分层落点

| 层 | 变化 |
|---|---|
| L4 接入层 | `接入层/入口.道` 新增一类「工具驱动执行」演示：声明 2~3 个道语言工具回调（如「查工单状态」「生成报告」）→ 注入执行器 → 打印工具调用记录；原有四类演示不变 |
| L3 应用层 | `应用层/执行.道` 的 `执行工单` 增加可选 `工具列表`／`工具回调`；`基础设施层/语言模型.道` 增加 `.支持工具()`／`.工具对话()` |
| L1 基础设施层 | 适配器把标准库 `工具定义`／`工具对话`／`工具结果` 封装为业务可用的中文方法，统一处理环境变量、惰性探测与降级 |
| 标准库 | `大模型.工具对话`（InterpreterBuiltin，固定 5 参）负责多轮循环、回调派发与 tool 消息回填 |

### 7.2 工具调用数据流

```text
L4 入口：声明工具回调 → 构造工具列表(工具定义) → 注入执行工单
  └─ L3 执行工单(单, 调度器, 预算, 报告回调, ..., 工具列表, 工具回调)
        └─ L1 语言模型.支持工具() → .工具对话(提示词, 工具列表, 回调, 系统提示)
              └─ 大模型.工具对话(客户端, 消息列表, 工具列表, 回调, 选项字典)
                    └─ Provider.chat_with_tools → 后端（ollama / openai / anthropic）
                          └─ 响应 tool_calls 归一化：
                               Provider  {"id","name","arguments"}（英文）
                               道语言    "工具调用":[{"编号","名称","参数"}]（中文）
                          └─ 逐个 回调(名称, 参数字典) → 结果文本
                          └─ 回填 role="tool"（tool_call_id=调用编号）消息
                          └─ 下一轮，直到无工具调用或达到「最大轮次」（默认 5）
```

**统一结构**：请求侧 tool 定义为 `{"type":"function","function":{...}}`；响应侧 Provider 为英文键 `{"id","name","arguments"}`，道语言为中文键 `{"编号","名称","参数"}`。`工具调用记录` 元素为 `{"名称","参数","结果"}`，随成功／失败字典一并返回。

### 7.3 兼容性与边界

- `执行工单` 既有导出签名保持向后兼容：不传工具参数时行为与第二轮完全一致。
- `工具列表` 与 `工具回调` 必须同时非空且 `.支持工具()` 为真才启用工具路径；否则沿用原「最多 1 次文本生成」逻辑。
- 工具失败一律降级不中断（见第四节表格），LLM 仍是增强项而非依赖。
- 所有标识符、注释与用户可见消息用中文；领域层契约保持只读。
- 运行与降级演示见《使用说明.md》第十章；独立最小示例见 `示例/AI对话/工具调用示例.道`。

## 八、运维视图（第四轮）

前七节描述**开发时**的分层依赖；本节补充**运行时 / 部署时**的进程与资源关系。第四轮把看板从「入口内渲染」升级为可独立启动的 HTTP 服务，并新增轻量守护。所有组件都运行在**本机（`127.0.0.1`）**，不涉及 GitHub、公网 webhook 或对外投递。

### 8.1 部署关系总览

```text
┌──────────────────── 运维视图（本机 127.0.0.1，非 GitHub）────────────────────┐
│                                                                              │
│  ① 看板服务进程：看板服务.道（L4）                                            │
│     └─ 创建服务器() → 看板.注册() → 启动(端口)  【更夫端口，默认 8765】          │
│         └─ 路由：GET /、/审计、/预算、/审计导出；POST /暂停                     │
│         └─ 基础设施层/看板.道：预算页() 成本仪表 + 审计导出() 中文键 JSON        │
│         └─ 读状态字典 ──▶ 基础设施层/存储.道 ──▶ SQLite（WAL）                  │
│                                                                              │
│  ② 守护进程：守护.道（L4，独立启动）                                          │
│     └─ 周期执行(5000ms) → 心跳：时间戳 + 工单统计（经 存储.统计()）             │
│     └─ 异常捕获后继续；仅应用层存活信号，不做进程拉起/重启                      │
│                                                                              │
│  ③ 业务进程：接入层/入口.道（L4，演示/常驻主体）                               │
│     └─ L3 各业务模块 ──▶ L1 基础设施层/存储.道 ──▶ SQLite（与①共享同一库）      │
│                       └─▶ L1 基础设施层/语言模型.道 ──▶ 大模型标准库            │
│                                                      └─▶ ollama（gemma4:e4b） │
│                       └─▶ 未启动/失败即降级为关键词规则与模板（见第四节）       │
│                                                                              │
│  ④ 外部守护（非本仓库）：shell / systemd / supervisor                          │
│     └─ 开机自启、异常重启、日志归集、资源限制；管理①③进程的生命周期            │
└──────────────────────────────────────────────────────────────────────────────┘
```

### 8.2 组件职责与依赖

| 组件 | 部署形态 | 职责 | 依赖 | 端口 / 配置 |
| --- | --- | --- | --- | --- |
| `看板服务.道` | 独立 L4 进程，可长驻 | 打开存储 → 组装状态字典与看板 → 注册路由 → 启动 HTTP 服务 | `基础设施层/看板.道`、`基础设施层/存储.道`、网络标准库 | `更夫端口`（默认 8765） |
| `守护.道` | 独立 L4 进程，可长驻 | 每 5 秒打印时间戳 + 工单统计心跳，异常后继续 | 调度标准库 `周期执行`、`基础设施层/存储.道.统计()` | 无端口 |
| `基础设施层/看板.道` | L1，被看板服务调用 | 渲染首页 / 审计页 / 预算页，导出审计 JSON，注册路由 | 状态字典（由上层组装），无业务层依赖 | — |
| `基础设施层/存储.道` | L1，共享组件 | SQLite（WAL）持久化：工单 / 触发 / 报告 / 决策 / 授权 / Outbox；统计 | 数据库标准库 | SQLite 库文件路径需可写 |
| `基础设施层/语言模型.道` | L1，被业务层按需调用 | 惰性探测、判断 / 对话 / 工具对话与失败降级 | 大模型标准库 → ollama | `OLLAMA_HOST`（默认 `http://localhost:11434`）、`OLLAMA_MODEL`（默认 `gemma4:e4b`） |
| shell / systemd / supervisor | 外部，非本仓库 | 进程生命周期管理 | 操作系统 | — |

**关键关系**：

- 看板服务与业务进程**共享同一个 SQLite 库**——看板只读状态字典并渲染，不写领域对象；它的「新鲜度」取决于存储层落库，不依赖业务进程内存。
- 守护与看板服务**互不依赖**；守护只调用存储统计打印心跳，便于外部监控判断「进程是否还活着 / 是否卡死」。
- LLM 只在业务进程内经 L1 适配器调用；看板服务与守护**不发起任何模型请求**，因此二者不依赖 ollama，ollama 未启动时照常工作。

### 8.3 守护的定位与生产边界

`守护.道` 是**轻量心跳**，而非进程管理器：它用 `周期执行(5000, 回调)` 每 5 秒打印一次含时间戳与工单统计的中文心跳，回调抛异常时捕获并继续下一周期。

道语言运行时**没有 fork / 进程重启原语**，因此守护**不做**以下事情：真实进程拉起与崩溃重启、僵尸进程回收、端口冲突处理、资源限额。要把演示升级为 7×24 服务，生产环境必须配合 shell / systemd / supervisor：

- **systemd / supervisor** 负责：开机自启、`Restart=on-failure` 异常重启、stdout/stderr 日志归集、内存 / 文件句柄限额、端口监听。
- **本仓库的守护**只承担「应用层存活信号」角色：外部监控抓取其心跳时间戳，若超过阈值未更新即判定业务进程卡死，再由 systemd 介入重启。
- 两者分工：**外层管生死，内层报状态**。不要把守护误当成生产守护进程管理器。

### 8.4 启动顺序与停止

1. 确认 SQLite 库文件所在目录可写（`基础设施层/存储.道` 的 `打开存储` 会建库 / 打开 WAL）。
2. 如需 LLM，先启动 ollama 并拉取 `gemma4:e4b`；不启动则自动降级（见第四节），不影响看板与守护。
3. 启动看板服务：`python ../../源码/main.py 看板服务.道`（需先 `cd 示例/更夫`），验证 `curl -i http://127.0.0.1:8765/预算` 返回 200。
4. 在另一个终端启动守护：`python ../../源码/main.py 守护.道`，观察每 5 秒心跳。
5. 按需运行入口演示或《使用说明.md》第十一章的混沌 / 压测脚本。
6. 停止：各终端按 `Ctrl-C`；**自检与演示结束后不要留下常驻后台进程**。
