## 1. 目标与非目标

**目标**：
1. Python 接口层新增 `ToolDefinition` / `ToolCall` 统一类型，`ChatRequest.tools` 与
   `ChatResponse.tool_calls` 从预留字段变为真正可用的数据通道；
2. 三个 Provider（ollama / openai / anthropic）实现 `chat_with_tools()`，把各家
   tool_calls 格式归一为统一结构；全部用 HTTP mock 测试，不打外网；
3. `大模型` 标准库新增中文桥接函数，道语言可声明工具、发起工具对话、自动执行工具回调；
4. 更夫 Worker 用工具调用驱动执行步骤（工具即"能力"），新增工具调用演示与回归用例。

**非目标**：真正的网络工具（文件写仓库、发 PR）、Function Calling 之外的 Agent 框架、
GitHub 事件源、改动领域层契约 `领域层/领域.道`。

## 4. Python 核心类型契约（主代理实现，所有子代理按此消费）

### 4.1 `dao/llm/types.py` 新增

```python
@dataclass
class ToolDefinition:
    """一个可调用工具的定义（与 Provider 无关的规范结构）。"""
    name: str                      # 工具名，英文标识符，如 "运行测试"
    description: str = ""          # 给模型看的中文用途说明
    parameters: dict = field(default_factory=dict)  # JSON Schema（英文键：type/properties/required）
    def to_dict(self) -> dict:     # 返回 OpenAI 风格 tool 字典：
        # {"type":"function","function":{"name":...,"description":...,"parameters":...}}

@dataclass
class ToolCall:
    """模型请求调用一次工具（已解析参数）。"""
    id: str                        # 调用编号；后端无 id 时由 Provider 按位置生成 "call_0" 等
    name: str                      # 工具名
    arguments: dict                # 已解码的参数字典（不是 JSON 字符串）
    def to_dict(self) -> dict:     # 中文键 {"编号":id,"名称":name,"参数":arguments}
```

### 4.2 既有类型扩展

- `ChatRequest.tools: list[dict] | None`：元素为 `ToolDefinition.to_dict()` 的结果
  （OpenAI 风格 function tool 字典）。各 Provider 自行转成后端格式。
- `ChatResponse.tool_calls: list[dict] | None`：元素为**统一规范** `{"id":..,"name":..,"arguments":{...}}`（英文键），
  由各 Provider 归一化后填入。
- `ChatResponse.to_dict()` 新增键 `"工具调用"`：值为
  `[{"编号":..,"名称":..,"参数":{...}}]`（中文键，供道语言直接消费）；
  无工具调用时为 `[]`（不是空/None）。其余键保持不变，**向后兼容**。

### 4.3 `dao/llm/base.py` 契约

- `Provider.chat_with_tools(self, request: ChatRequest) -> ChatResponse` 保持非抽象，
  默认仍抛 `UnsupportedError`；文档字符串写明"子类实现时须把 tool_calls 归一为
  `{"id","name","arguments"}` 并填入 ChatResponse.tool_calls"。
- 不改 `chat` / `chat_stream` / `list_models` 三个抽象方法。

## 5. Provider 实现契约（子代理 A / B）

### 5.1 统一输入输出

- 输入：`request.tools`（OpenAI 风格 tool 字典列表）与 `request.messages`。
- 输出：`ChatResponse`，其中 `tool_calls` 为统一规范列表（见 4.2）；`content` 可为模型
  附带的文本（可能为空串）；`usage` 正常填写；`finish_reason` 为后端原值（如 `tool_calls`）。
- **无 tools 时**：`chat_with_tools(request)` 行为应与 `chat(request)` 一致（可内部委托 `chat`）。
- 失败处理沿用既有约定：抛 `ProviderError` / `ConfigError`；不吞异常、不返回假响应。

### 5.2 子代理 A — ollama

- 文件：`dao/llm/providers/ollama.py`，新增 `chat_with_tools()`。
- ollama `/api/chat` 的 `tools` 字段与 OpenAI 风格兼容：`{"type":"function","function":{...}}`。
- 响应 `message.tool_calls` 形如 `[{"function":{"name":..,"arguments":{...}}}]`，
  **早期版本没有 id** → 用 `f"call_{i}"` 按位置生成；arguments 可能是 dict 或 JSON 字符串，
  字符串时用 `json.loads` 解码，解码失败当作空字典并保留原始内容到 `raw`。
- 测试 `tests/test_llm_tools_ollama.py`：用 `unittest.mock.patch` 拦截 `urllib.request.urlopen`
  或既有 patch 方式（参照 `tests/test_llm_ollama.py`），覆盖：① 有 tool_calls 的响应解析；
  ② 无 tools 时委托 chat；③ arguments 为 JSON 字符串的解码；④ usage 映射。≥ 8 项。

### 5.3 子代理 B — openai / anthropic

- 文件：`dao/llm/providers/openai.py`、`anthropic.py`，各新增 `chat_with_tools()`。
- OpenAI：请求体加 `tools`（原样传 `request.tools`）与 `tool_choice="auto"`；
  响应 `choices[0].message.tool_calls` 形如 `[{"id":..,"function":{"name":..,"arguments":"<json>"}}]`，
  解析 arguments JSON 字符串为 dict。
- Anthropic：请求体加 `tools`（需把 OpenAI 风格转成 Anthropic 风格：
  `{"name":..,"description":..,"input_schema":{...}}`）；响应 `content` 中 `type=="tool_use"`
  的块形如 `{"id":..,"name":..,"input":{...}}`，归一为统一结构。
- 测试 `tests/test_llm_tools_remote.py`：全部 HTTP mock，覆盖两家请求体拼装、
  响应解析、无 tools 委托、配置缺失报错。≥ 10 项。

## 6. 道语言桥接契约（主代理实现）

`dao/stdlib/llm.py` 新增 3 个中文函数（均返回中文键字典，失败返回 `{"成功":假,"错误":...}`）：

```
工具定义(名称, 描述="", 参数模式=空) -> 字典
  // 参数模式支持两种：
  //   ① 简化中文键 {"属性":{"城市":{"类型":"string","描述":"城市名"}},"必填":["城市"]}
  //   ② 标准英文 JSON Schema {"type":"object","properties":{...},"required":[...]}
  // 返回 OpenAI 风格 tool 字典（英文键），直接传给「工具对话」；名称须为非空文本。

工具对话(客户端, 消息列表, 工具列表, 回调函数, 选项字典) -> 字典
  // InterpreterBuiltin（参照「流式对话」，固定 5 个参数）：自动多轮循环——
  //   调 provider.chat_with_tools → 若有「工具调用」，逐个回调 回调函数(名称, 参数字典)，
  //   把返回的文本作为 tool 消息追加 → 再调，直到无工具调用或达到最大轮次。
  // 回调必须接受 2 个参数（名称、参数字典），返回工具执行结果文本。
  // 选项字典支持键「最大轮次」（正整数，默认 5）及「模型/温度/最大token」。
  // 返回 {"成功":真/假, "内容":最终文本, "工具调用记录":[{"名称":..,"参数":..,"结果":..}],
  //       "用量": 累计中文键用量, "轮次":n, "错误":文本}

工具结果(调用编号, 内容) -> 字典
  // 手动模式辅助：构造 role="tool" 消息（中文键 {"角色":"tool","内容":..,"调用编号":..}），
  // 供不用自动回调的高级用法。
```

实现约束：模块级函数 + `InterpreterBuiltin`（docgen 幂等）；不引入第三方包；
`最大轮次` 默认 5 且须为正整数，否则返回失败字典。

## 7. 更夫 Worker 工具调用集成（子代理 C）

保持现有导出签名**向后兼容**，只增加可选参数：

- `基础设施层/语言模型.道` 新增方法：
  - `.支持工具()` → 逻辑：模型对象非空且提供者支持工具调用（可用假对象模拟）。
  - `.工具对话(提示词, 工具列表, 回调, 系统提示="")` → 字典：把提示词包成消息，调 L1 桥接
    的 `工具对话`；失败时返回 `{"成功":假,...}`，不抛异常。
- `应用层/执行.道`：`执行工单(单, 调度器, 预算, 报告回调, 步骤列表=空, 语言模型=空)` 增加
  可选参数 `工具列表=空`、`工具回调=空`。当两者非空且 `.支持工具()` 为真时，用工具对话
  替代原"最多 1 次文本生成"作为末报告的结论来源；成功时末报告数据附
  `{"工具调用记录":[...], "模型来源":"ollama"}`，并把用量 token 计入预算；失败退回原模板。
- `接入层/入口.道`：新增一类演示"工具驱动执行"——定义 2~3 个道语言工具回调
  （如「查工单状态」「生成报告」），注入执行器，打印工具调用记录。原有四类演示保持不变。
- `测试/测试LLM接入.道`：新增 3~5 个工具调用用例（可用假语言模型对象/假回调模拟，
  不依赖真实 ollama），总数 13 → 16 以上。

**约束**：不得改 `领域层/领域.道`；LLM/工具失败一律降级不中断演示；所有标识符中文。
