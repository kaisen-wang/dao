# 17. 原生打包与安装（Nuitka）

> 更新：2026-11-20。把道语言解释器用 Nuitka 编译为**单文件原生可执行程序**，无需 Python 环境即可运行。

## 17.1 为什么用 Nuitka

默认的运行方式是 `python main.py`，要求用户本机装 Python 3.10+ 与依赖。对"想直接拿一个文件来用"的场景，Nuitka 把解释器连同标准库、dao 包、可选依赖一起编译为 C 再链接成一个 ELF 可执行文件：

- **零运行时依赖**：目标机器无需 Python、无需 pip，拷贝单个文件即可运行。
- **中文无损**：源码、异常与输出全部中文，产物行为与 Python 版逐字节一致（已实测，见 17.4）。
- **双模式保留**：AST 解释器与 `--mode vm`（含 JIT / 反汇编）在原生版中均可用。

## 17.2 环境与产物

| 项 | 值 |
|----|----|
| 编译器 | Nuitka 4.x + gcc（本机 gcc 15） |
| Python | 3.13.12（构建时），产物运行时无需 |
| 产物 | `dist/nuitka/dao`（Linux x86-64 ELF，约 47 MB，onefile 自解压压缩） |
| 构建耗时 | 首次约 5–8 分钟（591 个 C 源文件 + onefile payload 压缩） |

> `dist/` 已被 `.gitignore` 忽略，二进制不入库；需要时按 17.3 现场重建。

## 17.3 构建

```bash
# 一次性准备（隔离 venv）
cd 源码
./.venv/bin/python -m pip install 'nuitka>=2.5'

# 一键构建（可在仓库任意位置运行）
bash 源码/打包原生版.sh
```

脚本等价于：

```bash
cd 源码
./.venv/bin/python -m nuitka \
    --onefile \
    --include-package=dao \
    --output-filename=dao \
    --output-dir=../dist/nuitka \
    --assume-yes-for-downloads \
    main.py
```

关键参数说明：

- `--onefile`：把所有内容压进单个可执行文件，运行时解压到临时目录；
- `--include-package=dao`：**必须**。解释器用惰性导入（`from dao.bytecode...`、`prompt_toolkit` 等写在函数体内），显式包含整个包才能覆盖动态路径；
- 无需 `--standalone`（`--onefile` 已隐含）或 `no-qt` 之类插件，道语言不依赖 Qt。

构建目录（`main.build/` / `main.dist/` / `main.onefile-build/`）留在 `dist/nuitka/` 便于排查，可安全删除，只保留 `dao` 即可分发。

## 17.5 安装到系统 PATH

构建产物可直接运行：

```bash
dist/nuitka/dao --help
dist/nuitka/dao examples/你好世界.道
```

若希望像普通命令一样用 `dao`，用安装脚本（用户级无需管理员权限）：

```bash
# 安装到 ~/.local/bin/dao（推荐）
bash 源码/安装原生版.sh

# 若 ~/.local/bin 不在 PATH，加入 shell 配置：
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc

# 系统级安装（需 sudo，装到 /usr/local/bin/dao）
sudo bash 源码/安装原生版.sh --system

# 卸载（同时清理用户级与系统级）
bash 源码/安装原生版.sh --uninstall
sudo bash 源码/安装原生版.sh --uninstall
```

安装脚本会检查产物存在性、创建目标目录、设置可执行权限并做一次 `--help` 冒烟验证；卸载幂等，重复执行不报错。

## 17.6 使用

```bash
dao --version                # 显示版本号（等价于 -V）
dao                          # 启动 REPL
dao 你好世界.道              # 执行文件
dao --mode vm 斐波那契.道    # 字节码 VM 模式
dao --mode vm --jit --disasm 斐波那契.道  # JIT + 反汇编
dao --type-check 程序.道     # 启用类型推断检查
```

其余 REPL 命令（`:帮助`、`:宏列表`、多行粘贴等）与 Python 版完全相同。

### 版本信息的单一来源

版本号只在 `dao/version.py` 的 `__version__` 定义一次；`dao.__version__`（包元数据）、`--version`（命令行）、REPL 横幅都从它读取，避免多处硬编码漂移。

- `dao.version.version_text()` → `--version` 输出的中文单行文本；
- `dao.version.banner_text()` → REPL 横幅中的版本行；
- `dao/__init__.py` 从 `version` 重导出 `__version__`/`__author__`，保持既有 `import dao; dao.__version__` 用法不变。

**升级版本时只改 `dao/version.py` 一处即可**，原生版需重新构建才能带上新版本号。同步提醒：VS Code 插件的 `package.json` 有独立的 `version` 字段，发布插件时需另行对齐。

## 17.7 已知限制

- **平台绑定**：产物是 Linux x86-64 ELF；其他平台需在对应系统重新构建（Nuitka 不支持交叉编译）。
- **onefile 启动开销**：每次运行需自解压到临时目录，冷启动比 Python 版稍慢（约百毫秒级），换来的是单文件分发的便利。
- **首次杀毒误报**：onefile 的自解压行为可能被个别杀软误报，属已知现象。
- **体积**：47 MB 包含完整 dao 包与 prompt_toolkit；若不需要 REPL 行编辑，可移除 prompt_toolkit 依赖后重编以减小体积。
- **系统级安装需管理员权限**：`.deb`/`.pkg`/`setup.exe` 安装到系统目录均需 sudo/管理员；无权限时用 17.5 的用户级安装，或直接用 17.3 的单文件。

## 17.8 CI 自动构建系统级安装包

### 跨平台构建脚本

`源码/构建安装包.py` 统一调度「Nuitka onefile 编译 + 按平台打包」，GitHub Actions 与 Gitee Go 都调它：

```bash
cd 源码
python 构建安装包.py                    # 构建 + 打包（当前平台）
python 构建安装包.py --no-build         # 跳过编译，用已有 dist/nuitka 产物
python 构建安装包.py --arch-label arm64 # 覆盖架构标签（产物命名）
```

脚本从 `dao/version.py` 读版本号（单一来源），产物统一放 `dist/installers/`：

| 平台 | 系统级包 | 安装路径 | 依赖工具 |
|------|----------|----------|----------|
| Linux | `dao_{版本}_linux_{架构}.deb` | `/usr/bin/dao` | `dpkg-deb` |
| macOS | `dao_{版本}_macos_{架构}.pkg` | `/usr/local/bin/dao` | `pkgbuild`（Xcode CLT 自带） |
| Windows | `dao_{版本}_windows_{架构}_setup.exe` | `%ProgramFiles%\Dao\dao.exe` | Inno Setup（`iscc`） |

Linux 打包用 `--root-owner-group`，保证 CI 非 root 构建时包内文件属主仍为 root/root。

**Linux 的 `patchelf`**：Nuitka onefile 在 Linux 上必需它（修改 ELF 的 RPATH）。脚本会在编译前自动检测，缺失时通过 `python -m pip install patchelf` 补装（PyPI wheel 自带二进制，无需 sudo/apt），并把安装目录补进 PATH——因此干净的 CI runner 也能直接构建。CI 配置里也显式安装了它作为双保险。

### GitHub Actions（全平台主力）

`.github/workflows/build-installers.yml`：

- **矩阵**：`ubuntu-latest`（.deb）、`macos-13` Intel + `macos-14` Apple Silicon（.pkg）、`windows-latest`（setup.exe）；
- **触发**：推 `v*` 标签 → 构建并创建 Release；手动 `workflow_dispatch` → 仅上传 artifact；推 `main` / PR → 仅跑全量测试（省 CI 时长）；
- **流程**：测试 → 四平台构建（含原生 `--version` 冒烟）→ 上传 artifact → tag 触发时 `softprops/action-gh-release` 发布；
- Windows  runner 需 `choco install innosetup` 并把 Inno Setup 加入 `PATH`。

**前置**：GitHub 上需有仓库并推送本配置（当前 `git remote` 指向 Gitee，需先添加 GitHub remote 或迁移）。

### Gitee Go（兼容配置）

`.workflow/build-installers.yml` 使用 Gitee Go 自有流水线格式（`stages`/`steps`，与 GitHub Actions 不兼容）：

- Gitee 托管构建机默认只有 Linux，故产出 **Linux .deb** 并通过 `release@gitee` 插件发到 Gitee Release；
- macOS/Windows 需在「Gitee Go → 自有主机」注册 Runner 并把 `executor` 指向对应主机组，才能产出全平台包；
- `assertFiles` 用 `dist/installers/*.deb` 通配符，避免硬编码版本号。

> 两套 CI 并行维护、互不干扰：GitHub Actions 负责全平台发布，Gitee Go 负责国内镜像的 Linux 包。

### 本地验证记录（2026-11-20）

在 Ubuntu 本机实测 Linux 路径：

```bash
cd 源码 && python 构建安装包.py --no-build
dpkg-deb -I dist/installers/dao_1.0.1_linux_x86_64.deb   # 元数据：版本 1.0.1 / amd64 / root 属主
dpkg-deb -x dist/installers/dao_1.0.1_linux_x86_64.deb /tmp/x
/tmp/x/usr/bin/dao --version                              # 道（Dao）编程语言 v1.0.1
```

结果：包元数据正确、解压后可执行文件可运行且与源 onefile 逐字节一致。macOS/Windows 包需在对应 CI runner 上生成，本地无法交叉构建（Nuitka 不支持交叉编译）。
