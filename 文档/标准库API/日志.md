# 日志模块 API

模块路径：`日志`

## 导入方式

```
从 日志 导入 配置日志, 默认格式, 创建日志器, 创建文件处理器, 创建控制台处理器
导入 日志
```

> 标准库函数须用 `从 模块 导入 名称` 形式；`导入 日志` 不会导出内置函数。

## 快速开始

```
从 日志 导入 配置日志, 默认格式

日志器 = 配置日志(输出="两者", 路径="应用.log", 格式=默认格式, 级别="信息")
日志器.信息("服务启动")
```

`默认格式` 为 `{级别} {时间戳} {线程ID} {代码位置} | {描述信息}`，输出形如：

```
INFO 2026-11-28 09:12:03,123 140245328901120 入口.道:12 | 服务启动
```

## 函数列表

### 配置日志

一步配置日志器：选定输出目标、格式、级别与时间格式，返回可直接使用的日志器。重复配置同名日志器会重置其原有处理器，避免同一条日志被重复写出。

**签名**：`配置日志(名称="道", 输出="控制台", 路径=空, 格式=默认格式, 级别="信息", 时间格式=空) -> DaoLogger`

**参数**：
- `名称`：日志器名称（同名日志器共享配置）
- `输出`：`控制台` / `文件` / `两者`
- `路径`：输出含`文件`时必填，指定日志文件路径
- `格式`：格式字符串，见下方占位符表；默认使用 `默认格式`
- `级别`：`调试` / `信息` / `警告` / `错误` / `致命`
- `时间格式`：strftime 风格时间格式，如 `%Y年%m月%d日 %H:%M:%S`

**异常**：`运行时错误`：输出方式无效、文件输出缺少路径、级别无效

**示例**：
```
从 日志 导入 配置日志
日志器 = 配置日志(输出="文件", 路径="应用.log", 级别="警告")
日志器.警告("磁盘空间不足")
```

---

### 创建日志器

创建一个指定名称的日志器，可选设置默认代码位置。需自行添加处理器才能输出。

**签名**：`创建日志器(名称: 文本) -> DaoLogger`

**参数**：
- `名称`：日志器名称

**示例**：
```
从 日志 导入 创建日志器, 创建控制台处理器
日志器 = 创建日志器("我的应用")
日志器.添加处理器(创建控制台处理器())
日志器.信息("程序启动")
```

---

### 创建文件处理器

创建写入指定路径文件的日志处理器，可单独指定格式与时间格式。

**签名**：`创建文件处理器(路径: 文本, 格式=空, 时间格式=空) -> DaoFileHandler`

**参数**：
- `路径`：日志文件路径
- `格式`：可选，仅作用于本处理器
- `时间格式`：可选，strftime 风格

**异常**：`运行时错误`：无法创建日志文件

**示例**：
```
定义 文件处理器 = 创建文件处理器("app.log", "{时间} {级别} {消息}")
```

---

### 创建控制台处理器

创建输出到控制台（标准错误流）的日志处理器，可单独指定格式与时间格式。

**签名**：`创建控制台处理器(格式=空, 时间格式=空) -> DaoConsoleHandler`

**示例**：
```
定义 控制台处理器 = 创建控制台处理器()
```

## 自定义类型

### DaoLogger

日志器对象，提供分级日志、格式设置与多处理器输出。

**方法**：

| 方法名 | 签名 | 说明 |
|--------|------|------|
| `调试` | `调试(消息)` | 输出调试级别日志 |
| `信息` | `信息(消息)` | 输出信息级别日志 |
| `警告` | `警告(消息)` | 输出警告级别日志 |
| `错误` | `错误(消息)` | 输出错误级别日志 |
| `致命` | `致命(消息)` | 输出致命级别日志 |
| `记录` | `记录(级别, 消息)` | 按中文级别名分派 |
| `设置级别` | `设置级别(级别)` | 设置最低输出级别 |
| `添加处理器` | `添加处理器(处理器)` | 添加输出处理器，同一对象或同一文件不重复添加 |
| `设置格式` | `设置格式(格式, 时间格式=空)` | 设置所有处理器的格式 |

**日志级别**：

| 道语言级别 | 说明 | 数值 |
|-----------|------|------|
| `调试` | 调试信息 | 10 |
| `信息` | 一般信息 | 20 |
| `警告` | 警告信息 | 30 |
| `错误` | 错误信息 | 40 |
| `致命` | 致命错误 | 50 |

**格式占位符**：

| 占位符 | 说明 |
|--------|------|
| `{时间戳}` / `{时间}` | 时间戳（默认 `年-月-日 时:分:秒,毫秒`） |
| `{日志级别}` / `{级别}` | 日志级别（DEBUG / INFO / WARNING / ERROR / CRITICAL） |
| `{线程ID}` | 当前线程 ID |
| `{线程名}` | 当前线程名 |
| `{代码位置}` / `{位置}` | 调用位置（相对于命令执行目录的路径:行号），由解释器自动注入 |
| `{描述信息}` / `{描述}` / `{消息}` | 日志正文 |
| `{名称}` | 日志器名称 |
| `{文件名}` / `{行号}` / `{函数名}` | Python logging 原生字段（调试用） |

> 格式中的字面 `%` 会自动转义，可直接写 `完成 100% {消息}`。
> `{代码位置}` 由解释器在调用日志方法时自动注入（相对于命令执行目录的路径:行号），无需调用者传入；直接通过 Python 调用且无调用点上下文时为空。

**异常**：`运行时错误`：设置无效的日志级别、处理器类型无效

**示例**：
```
从 日志 导入 配置日志, 默认格式
日志器 = 配置日志(输出="文件", 路径="应用.log", 格式=默认格式)
日志器.信息("程序启动")
日志器.错误("连接失败")
日志器.记录("警告", "重试第 2 次")
```

## 结构化日志（OpenTelemetry 风格）

上一节介绍的是**文本日志（text logging）**：把消息格式化成一行人类可读的字符串。
本节介绍新增的**结构化日志（structured logging）**：把每条日志当作一个**事件（event）**
来处理，输出机器可读的 JSON，并携带时间戳、严重性、属性、资源、作用域与追踪关联信息。
字段命名与序列化格式参考 OpenTelemetry Logs Data Model，便于 Collector 与后端直接消费。

### 与文本日志的区别

| 对比项 | 文本日志 | 结构化日志 |
|--------|----------|------------|
| 输出形态 | 一行格式化字符串 | 一行 JSON（JSON Lines） |
| 可检索性 | 需正则解析字符串 | 字段可直接查询、聚合 |
| 上下文 | 拼在消息文本里 | 以扁平 `属性` / `资源` 承载 |
| 严重性 | `INFO` / `WARNING` 等字符串 | `SeverityText` + `SeverityNumber`（0-255） |
| 追踪关联 | 需手工把 TraceId 写进消息 | 自动注入 `TraceId` / `SpanId` |
| 处理方式 | 格式化后直接写出 | 处理器链过滤 / 脱敏 / 采样后再导出 |
| 典型用途 | 本地开发、人工排错 | 日志平台、告警、链路追踪 |
| 核心函数 | `配置日志` | `配置结构化日志` |

两者可以共存：同一程序里既用 `配置日志` 输出可读文本，又用 `配置结构化日志`
输出 JSON，互不干扰（使用不同的日志器名称即可）。

> 术语约定：下文保留 `LogRecord`、`Body`、`Attributes`、`Resource`、`Scope`、
> `TraceId`、`SpanId`、`SeverityNumber` 等英文原名，并在首次出现时给出中文解释。

### 日志事件字段（LogRecord）

每条记录是一个 `LogRecord`（日志记录），字段如下（键名遵循 OpenTelemetry 规范）：

| 字段名（JSON 键） | 英文原名 | 中文解释 | 示例 |
|------------------|----------|----------|------|
| `timestamp` | Timestamp | 事件发生时间，UTC ISO-8601，毫秒精度，以 `Z` 结尾 | `2026-11-28T09:12:03.123Z` |
| `observed_timestamp` | ObservedTimestamp | 采集系统观察到该事件的时间（可能与发生时间不同） | `2026-11-28T09:12:03.124Z` |
| `severity_number` | SeverityNumber | 严重性数值，0-255，越大越严重 | `9` |
| `severity_text` | SeverityText | 严重性文本 | `INFO` |
| `body` | Body | 日志正文，即消息文本 | `支付成功` |
| `attributes` | Attributes | 扁平化上下文属性，键建议点分隔 | `{"user.id": "123"}` |
| `resource` | Resource | 产生日志的实体元数据 | `{"service.name": "支付服务"}` |
| `scope` | Scope | 产生日志的组件信息（库名、版本） | `{"name": "服务"}` |
| `trace_id` | TraceId | 32 位十六进制追踪 ID，关联一次分布式请求 | `4bf92f3577b34da6a3ce929d0e0e4736` |
| `span_id` | SpanId | 16 位十六进制跨度 ID，关联请求中的一个操作 | `00f067aa0ba902b7` |
| `location` | — | 道语言调用位置（相对命令执行目录的 `路径:行号`），由解释器注入 | `示例/结构化日志/快速开始.道:12` |

严重性映射（中文级别 → `SeverityText` / `SeverityNumber`）：

| 道语言级别 | SeverityText | SeverityNumber 区间起点 |
|-----------|--------------|--------------------------|
| `调试` | `DEBUG` | 5 |
| `信息` | `INFO` | 9 |
| `警告` | `WARN` | 13 |
| `错误` | `ERROR` | 17 |
| `致命` | `FATAL` | 21 |

`severity_of` 同时接受中文级别、英文文本（`DEBUG` / `WARN` / `WARNING` / `CRITICAL`
等）与数字字符串，无效值抛出 `运行时错误`。

### JSON 输出示例

配置结构化日志并输出一条记录，得到的单行 JSON 如下（为便于阅读做了缩进）：

```json
{
  "timestamp": "2026-11-28T09:12:03.123Z",
  "observed_timestamp": "2026-11-28T09:12:03.124Z",
  "severity_number": 9,
  "severity_text": "INFO",
  "body": "支付成功",
  "attributes": {"user.id": "123", "order.id": "456", "环境": "生产"},
  "resource": {"service.name": "支付服务", "host.name": "node-1"},
  "scope": {"name": "服务"},
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "location": "示例/结构化日志/快速开始.道:12"
}
```

`to_json()` 默认保留中文原文（`ensure_ascii=False`），适合直接写入文件；
下游系统可按 `severity_text`、`attributes.*`、`resource.*`、`trace_id` 等字段建索引。

### 新增函数

#### 配置结构化日志

一步配置结构化日志器，返回 `DaoStructuredLogger`（结构化日志器）。

**签名**：`配置结构化日志(名称="道", 输出="控制台", 路径=空, 级别="信息", 资源=空, 处理器=空, 批量大小=1, 异步=假) -> DaoStructuredLogger`

**参数**：
- `名称`：日志器名称，决定 `scope.name`，同名日志器共享配置
- `输出`：`控制台` / `文件` / `两者` / `内存`；导出为 JSON Lines。`内存` 配合 `取记录()` 使用
- `路径`：输出含 `文件` 时必填，指定日志文件路径
- `级别`：最低输出级别（`调试` / `信息` / `警告` / `错误` / `致命`）
- `资源`：静态资源属性字典，自动合并到每条记录的 `resource`
- `处理器`：处理器列表，按顺序组成处理器链（见下节）
- `批量大小`：一次导出的记录条数，默认 1（逐条写出）
- `异步`：是否使用异步批量导出，默认 `假`

**异常**：`运行时错误`：输出方式无效、文件输出缺少路径、级别无效、处理器类型无效

`输出="内存"` 时不写文件、不输出控制台，可直接用 `取记录()` 查看结构化记录，适合测试与调试：

```
从 日志 导入 配置结构化日志

日志器 = 配置结构化日志(名称="测试", 输出="内存")
日志器.信息("支付成功", 属性={"user.id": "123"})
记录列表 = 日志器.取记录()   // 字典列表，含 body / attributes / severity_text 等字段
日志器.关闭()
```

#### 日志器方法

结构化日志器 `DaoStructuredLogger` 提供以下方法：

| 方法名 | 签名 | 说明 |
|--------|------|------|
| `调试` | `调试(消息, 属性=空)` | 记录 DEBUG 事件 |
| `信息` | `信息(消息, 属性=空)` | 记录 INFO 事件 |
| `警告` | `警告(消息, 属性=空)` | 记录 WARN 事件 |
| `错误` | `错误(消息, 属性=空)` | 记录 ERROR 事件 |
| `致命` | `致命(消息, 属性=空)` | 记录 FATAL 事件 |
| `记录` | `记录(级别, 消息, 属性=空)` | 按中文级别名记录事件 |
| `刷新` | `刷新()` | 刷新缓冲区，确保未导出的记录写出 |
| `关闭` | `关闭()` | 关闭导出器与文件句柄，重复调用安全 |
| `取记录` | `取记录()` | 返回已记录事件的字典列表，便于测试与调试；需 `输出="内存"` 或传入内存导出器 |

`属性` 为扁平字典，键建议点分隔命名（如 `user.id`、`order.id`、`http.status_code`）。
`location` 由解释器自动注入，调用者无需传入。

#### 创建追踪 / 取追踪头 / 载入追踪头

追踪上下文（TraceContext）用于把日志与一次分布式请求关联。

- `创建追踪(属性=空, 追踪ID=空, 跨度ID=空) -> 追踪上下文`：创建并激活一条新追踪，`属性` 成为 baggage
  （请求级元数据，如租户 ID）；TraceId / SpanId 默认自动生成，也可显式传入以对接已有链路。
- `取追踪头() -> 文本`：返回当前追踪的 W3C `traceparent` 头文本，无追踪时返回空文本，
  用于注入到下游 HTTP 请求头。返回值同时支持字典式访问：`头["traceparent"]` 取追踪头、
  `头["baggage"]` 取请求级元数据；两者可直接作为 HTTP 请求头使用。
  （Python 侧还可用 `头.to_dict()` 得到普通字典。）
- `载入追踪头(头) -> 追踪上下文或空`：从上游传来的 `traceparent` 字符串或请求头字典
  解析并激活为当前追踪上下文；格式无效或全零 ID 时返回 `空`（不抛异常）。

`traceparent` 遵循 W3C Trace Context 标准，格式为
`00-<32位TraceId>-<16位SpanId>-<2位标志>`（如
`00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-00`）。
版本 `ff`、全零 ID、格式不合法的值会被拒绝。

```
追踪 = 创建追踪(属性={"租户": "acme"})
头 = 取追踪头()        # "00-4bf92f...-00f067aa...-00"
头["traceparent"]     # 同上，字典式访问
头["baggage"]         # "租户=acme"
// 把 头 作为 traceparent 请求头发送到下游服务；下游用 载入追踪头(头) 恢复上下文
```

#### 设置资源

`设置资源(服务名=空, 主机名=空, 环境=空, 属性=空) -> 资源`：设置全局资源元数据
（Resource）；未指定的字段保留上一次的值，`属性` 与已有属性合并。
可用字段自动映射为 OTel 语义约定键：`服务名` → `service.name`、
`主机名` → `host.name`、`环境` → `environment`。

#### 处理器工厂

处理器（Processor）在记录导出前依次对其进行处理：可修改记录后返回，
也可返回 `空` 丢弃该记录。工厂函数如下：

- `创建属性处理器(属性=空)`：把静态属性合并到每条记录，已有键优先保留（AttributeInjector）。
- `创建脱敏处理器(键=空, 模式=空, 掩码="***")`：按属性名（子串或点分段名，忽略大小写）
  或正则 `模式` 命中的值替换为掩码，并对正文做正则替换（Redaction / 脱敏）。
  > 注意：`规则` 是道语言关键字，不能作参数名；Python 侧函数保留 `规则` 作为 `模式` 的别名，
  > 道语言脚本请统一使用 `模式=`。
- `创建采样处理器(比率=1.0, 保留错误=真)`：按 `比率` 随机采样；`保留错误` 为真时
  ERROR / FATAL 记录始终保留（Sampling / 采样）。`比率` 必须在 0 到 1 之间。
  `比率` 的别名为 `比例`，两者等价，同时传入时以 `比率` 为准。
- `创建内存导出器()`：创建内存导出器（MemoryExporter），把记录收集在内存中，
  常用于测试与调试；配合 `取记录()` 读取（也可直接令 `输出="内存"`）。

**处理器链**：记录按 `处理器` 列表顺序流经每个处理器；任一处理器返回 `空`
即丢弃该记录、不再继续。典型顺序为：

```
属性注入 → 脱敏 → 采样 → 追踪/资源注入 → 导出
```

`资源` 与 `处理器` 的区别：`资源` 是静态元数据（整条日志共享），
`属性` 是单条事件的上文；两者最终分别写入 `resource` 与 `attributes` 字段。

完整示例（更多可运行示例见 `示例/结构化日志/`）：

```
从 日志 导入 配置结构化日志, 创建属性处理器, 创建脱敏处理器, 创建采样处理器

日志器 = 配置结构化日志(
    名称="服务",
    输出="文件",
    路径="应用.日志",
    级别="信息",
    资源={"服务名": "支付服务"},
    处理器=[
        创建属性处理器(属性={"环境": "生产"}),
        创建脱敏处理器(键=["user.id", "phone"]),
        创建采样处理器(比率=0.5),
    ],
)
日志器.信息("支付成功", 属性={"user.id": "123", "order.id": "456"})
日志器.刷新()
日志器.关闭()
```

### 采样与脱敏实践

- **脱敏（Redaction）**：在日志离开进程前清除 PII（ personally identifiable
  information，个人身份信息）。优先按属性键脱敏（如 `user.id`、`phone`、`id_card`），
  也可提供正则对正文中的号码、邮箱做替换。脱敏应放在采样之前，确保任何被导出的记录都已处理。
- **采样（Sampling）**：高流量服务按 `比率` 采样以降低存储成本；`保留错误=真`
  保证错误与致命事件 100% 保留，避免采样丢失关键告警。
- **顺序**：`属性注入 → 脱敏 → 采样 → 导出`，保证每条被写出的记录都已被脱敏，
  且采样不会丢弃错误事件。

### OTLP 导出与 Collector 对接

OpenTelemetry Collector 是集中处理节点，负责汇聚、清洗、增强与路由日志。
`OTLPHTTPExporter` 把 `LogRecord` 转为 OTLP/HTTP JSON（结构为
`resourceLogs → scopeLogs → logRecords`）并 POST 到 Collector 的日志端点
（默认 `http://localhost:4318/v1/logs`）。

- `创建OTLP导出器(端点, 头=空, 超时=5.0) -> OTLPHTTPExporter`：创建 OTLP/HTTP JSON 导出器。
  - `端点`：Collector 的 OTLP/HTTP 日志接收地址，不能为空
  - `头`：额外请求头字典（如鉴权头），默认 `Content-Type: application/json`
  - `超时`：请求超时秒数
- `配置结构化日志(..., 导出器=导出器)`：把导出器交给结构化日志器；传入后实际导出目标
  由 `导出器` 决定，`输出` 仅用于参数合法性校验。

```
从 日志 导入 配置结构化日志, 创建OTLP导出器, 设置资源

设置资源(服务名="支付服务", 环境="生产")
导出器 = 创建OTLP导出器("http://localhost:4318/v1/logs")
日志器 = 配置结构化日志(输出="控制台", 导出器=导出器)
日志器.信息("支付成功", 属性={"order.id": "456"})
日志器.刷新()
日志器.关闭()
```

> OTLP 导出失败会抛中文 `运行时错误`（含 HTTP 状态码或网络原因）；生产环境建议
> 配合重试与降级策略，避免日志故障影响业务主流程。

### 尾部采样

头部采样（进入时按比率丢弃）可能丢掉后来变成错误的整条链路。尾部采样
（`TailSamplingExporter`）先按 TraceId 聚合一批记录，导出前再统一决策：

- 链路中任一记录为 ERROR / FATAL 且 `保留错误=真` → **整条链路全部导出**
- 其他链路按 `比率` 做一次整体采样（全保留或全丢弃）
- 无 TraceId 的记录不进入聚合，立即按比率决策

- `创建尾部采样导出器(导出器, 比率=1.0, 保留错误=真, 最大追踪数=1000) -> TailSamplingExporter`
  - `导出器`：被包装的真实导出器（OTLP / 文件 / 内存均可）
  - `最大追踪数`：缓冲上限，达到后触发一次决策

```
从 日志 导入 配置结构化日志, 创建内存导出器, 创建尾部采样导出器, 创建追踪

导出器 = 创建尾部采样导出器(创建内存导出器(), 比率=0.1, 保留错误=真)
日志器 = 配置结构化日志(输出="内存", 导出器=导出器)
创建追踪()
日志器.信息("常规请求")     # 大概率被采样丢弃
日志器.错误("支付失败")     # 整条链路必定保留
日志器.刷新()
```

### 环境变量集中配置

生产环境推荐把服务共享配置放到环境变量，避免在业务代码里分散初始化。

- `从环境加载资源() -> Resource`：读取环境变量并激活为全局资源元数据。

| 环境变量 | 对应字段 |
| --- | --- |
| `OTEL_SERVICE_NAME` | `service.name`（默认「道应用」） |
| `OTEL_RESOURCE_ATTRIBUTES` | 逗号分隔的 `key=value`，解析为资源属性 |
| `HOSTNAME` | `host.name` |
| `DEPLOY_ENV` / `ENVIRONMENT` | `environment` |

> Python 侧的 `get_resource()` 首次调用时也会自动从环境变量加载；显式调用
> `设置资源(...)` 优先于环境变量。该约定与 OpenTelemetry SDK 保持一致，
> 便于容器编排平台统一注入。

### 生产实践建议

1. **低基数事件名（low-cardinality event name）**：`body` 用稳定的事件名，
   如 `支付成功` / `订单创建`，不要把订单号、用户 ID 拼进正文，否则无法聚合；
   变化的值放到 `属性` 里。
2. **扁平属性（flat attributes）**：属性键用点分隔的扁平结构（如 `user.id`、
   `http.status_code`），避免嵌套对象，便于日志平台建索引与查询。
3. **PII 脱敏**：对手机号、身份证、邮箱、银行卡等字段统一使用脱敏处理器，
   配置集中管理，避免每个调用点各自处理导致遗漏。
4. **配置集中化**：在程序入口一次性调用 `配置结构化日志` 与 `设置资源`，
   不要在业务代码里分散配置；资源（服务名、主机名、环境）全局共享，属性随事件携带。
5. **追踪关联**：在请求入口 `创建追踪` 或 `载入追踪头`，在出口 `取追踪头`，
   让日志自动带上 `TraceId` / `SpanId`，实现日志与链路的双向跳转。
6. **资源与生命周期**：程序退出前调用 `刷新()` 与 `关闭()`，确保缓冲区记录全部写出、
   文件句柄正确释放。
