## 19.1 背景与目标

PRD 中至少三处要调大模型：**FR-03 语义评估 Eval**（轻量模型、按 Thread 串行）、**FR-08 Worker 执行**（最强模型、独立会话）、**FR-16 Watchdog 巡检**；NFR 还要求按档位分模型、按票统计成本。没有统一接口，每个调用点都得自己拼 HTTP、解析响应、处理错误。现有 `示例/AI对话/` 正是这种写法——`网络.请求` + `编码.JSON` 直接打 ollama 的 `/api/chat`、`/api/tags`（文档 18 §18.2、§18.8）。

问题在于：换后端要改所有业务代码；流式与非流式回调约定各自为政；`thinking`、`usage`、工具调用字段没有稳定形状；错误不统一，Eval/Worker 无法可靠降级。

**目标**：在道语言业务与后端之间插入一层稳定契约，做到「换 Provider 不改业务」。本次交付：Python 核心 `dao/llm/`（数据模型 + Provider 抽象 + 工厂）；三个 Provider（`ollama` 完整实现用于本机调试，`openai` / `anthropic` 为骨架）；道语言标准库「大模型」模块（中文函数与中文字典键）；`示例/AI对话/接口层示例.道`。

**范围边界**：先打通 ollama 调试链路，预留 OpenAI / Anthropic 扩展位；**不做 GitHub**（事件适配器、webhook 归一化），不做 Web 面板、工具调用协议与成本熔断。

> 注（第三轮，2026-11-22）：上述范围边界属于**第二轮交付时的快照**，保留原文以记录决策依据。工具调用协议已在本轮补全并落地，详见 §19.10；GitHub、Web 面板与成本熔断仍不在本层范围内。

## 19.3 数据模型详解

均定义于 `dao/llm/types.py`。**关键约定：`ChatMessage.to_dict()` 返回英文键**（供 Provider 拼请求体）；**`ChatResponse` / `Usage` / `StreamChunk` 的 `to_dict()` 返回中文键**（供道语言消费）。用途不同，勿混用。

**ChatMessage（types.py:33-75）**：`role`、`content`、`thinking`（思考过程）、`name`、`tool_call_id`、`tool_calls`（后两者为 Function Calling 预留；第三轮已启用，见 §19.10）。`__post_init__` 校验 `role ∈ {system, user, assistant, tool}`，非法值抛 `ValueError`。`to_dict()` 始终含英文键 `role`/`content`，有值时追加 `thinking`/`name`/`tool_call_id`/`tool_calls`；`from_dict()` 从英文键还原，缺字段取安全默认（`user`、空串）。便捷构造器：`user(content)` / `system(content)` / `assistant(content)`（types.py:78-90）。注：当前 ollama Provider 请求侧只发送 `role`/`content`，**不把 `thinking` 回传**；多轮历史应放最终 `content` 而非 thinking（与 gemma4 官方建议一致）。

**ChatRequest（types.py:150-165）**：`messages: list[ChatMessage]`（必填）、`model`、`temperature`、`top_p`、`max_tokens`、`stream`（默认 `False`）、`stop`、`tools`（第三轮由预留字段启用为真正的数据通道，见 §19.10）、`options`（后端特有参数透传）；`add_message(msg)` 追加消息。

**ChatResponse（types.py:168-204）**：`content`、`model`、`role`（默认 `assistant`）、`thinking`、`usage: Usage`、`finish_reason`、`tool_calls`、`raw`（原始响应，调试与统计用）。`to_dict()` 返回道语言可直接消费的中文键，第三轮新增 `工具调用` 键：

```json
{"内容": "……", "模型": "gemma4:e4b", "角色": "assistant",
 "思考": "……", "完成原因": "stop",
 "用量": {"提示token": 12, "生成token": 339, "总token": 351},
 "成功": true,
 "工具调用": [],
 "原始": {}}
```

`工具调用` 元素为 `{"编号": ..., "名称": ..., "参数": {...}}`（中文键，来自 `ToolCall.to_dict()`）；无工具调用时为 `[]` 而非 `None`，新增键不影响既有消费方（向后兼容）。

**StreamChunk（types.py:162-173）**：流式增量块 `content`（增量片段）、`thinking`（增量思考）、`done`、`raw`；`to_dict()` → `{"内容": ..., "思考": ..., "完成": ...}`。`content` 是**增量**，调用方需自行拼接；`done` 为真的块通常才带完整用量。

**Usage（types.py:93-109）**：`prompt_tokens` / `completion_tokens` / `total_tokens` / `extra`；`to_dict()` → `提示token` / `生成token` / `总token`，并把 `extra` 展开到同一层。ollama 的字段映射：`prompt_tokens` ← `prompt_eval_count`，`completion_tokens` ← `eval_count`，`total_tokens` ← 响应的 `total_tokens`（无则两者相加），`extra` ← `total_duration` / `load_duration` / `prompt_eval_duration` / `eval_duration` / `created_at`（存在才填）。

**异常层次（types.py:17-30）**：

```text
Exception
└── LLMError              接口层异常基类
    ├── ProviderError     网络 / HTTP 错误 / 响应格式异常
    ├── ConfigError       配置缺失或非法（含未知提供者名）
    └── UnsupportedError  不支持的能力（如工具调用）
```

## 19.4 Provider 契约

`Provider` 抽象基类定义于 `dao/llm/base.py:15-44`。子类经 `@register_provider("名字")` 注册；构造参数由各 Provider 自定义，统一收进 `self.config`。

| 方法 | 签名 | 语义 |
|---|---|---|
| `chat` | `chat(request: ChatRequest) -> ChatResponse` | 同步对话，返回完整响应（**抽象，必须实现**） |
| `chat_stream` | `chat_stream(request, on_chunk: OnChunk) -> ChatResponse` | 流式：逐块回调，返回累积后的完整响应（**抽象，必须实现**） |
| `list_models` | `list_models() -> list[str]` | 列出后端可用模型名（**抽象，必须实现**） |
| `chat_with_tools` | `chat_with_tools(request) -> ChatResponse` | 工具调用扩展点；**基类默认抛 `UnsupportedError`**（第三轮三个 Provider 均已实现，见 §19.10） |

`OnChunk = Callable[[StreamChunk], bool | None]`（base.py:12）：回调返回 `False` 表示调用方要提前终止流，Provider 应停止读取并立即返回已累积内容；返回 `None` 或真值继续。

`chat_with_tools` 在第二轮交付时**未实现**，对应 PRD FR-03 / FR-08 未来的 Function Calling / Tool Use，也是文档 18 §18.4 的「有原语没预制件」缺口。预留它是为了让工具协议落地时只改 Provider 与桥接层，调用点不动。

> 注（第三轮）：该缺口已补齐——三个 Provider 均实现 `chat_with_tools`，桥接层新增三个中文函数，调用点无需改动，详见 §19.10。本段保留第二轮表述作为历史记录。

## 19.5 工厂与扩展指南

`factory.py` 的三个公共函数：

- `@register_provider(name)`：登记 Provider 类并把其 `name` 属性设为 `name`（factory.py:13-24）。
- `create_provider(name, **config) -> Provider`：按名创建实例；名称不存在抛 `ConfigError` 并列出**当前可用提供者名**（factory.py:32-42）。
- `available_providers() -> list[str]`：返回排序后的已注册名称（factory.py:45-48）。

`_ensure_providers()` 惰性导入 `providers` 包触发自注册，避免循环导入；调用方无需手动导入具体 Provider。

**已注册名称与配置项**（`ollama` 已实现，`openai` / `anthropic` 为骨架）：

| 名称 | 配置项 | 默认值 | 说明 |
|---|---|---|---|
| `ollama` | `host` | `http://localhost:11434` | 服务地址 |
| | `model` | `gemma4:e4b` | 默认模型 |
| | `timeout` | `120` | 超时（秒） |
| `openai` | `api_key` | 环境变量 `OPENAI_API_KEY` | 缺省时从环境变量读取，缺失抛 `ConfigError` |
| | `base_url` | `https://api.openai.com/v1` | 可指向兼容网关 |
| | `model` | `gpt-4o-mini` | 可被 `request.model` 或配置覆盖 |
| | `timeout` | `120` | 超时（秒） |
| `anthropic` | `api_key` | 环境变量 `ANTHROPIC_API_KEY` | 缺省时从环境变量读取，缺失抛 `ConfigError` |
| | `base_url` | `https://api.anthropic.com/v1` | 可指向兼容网关 |
| | `model` | `claude-3-5-haiku-latest` | 可被 `request.model` 或配置覆盖 |
| | `timeout` | `120` | 超时（秒） |

配置取值优先级：**构造参数 > 环境变量 > 内置默认**；`host` 自动去掉尾部 `/`，`timeout` 无对应环境变量。`ollama` 的失败统一抛 `ProviderError`（HTTP 错误、非 200、URLError、非法 JSON、响应体 `error` 字段）；`ConfigError` 由工厂在未知提供者名时抛出。流式 `on_chunk` 自身抛出的异常原样上抛，不包装成 `ProviderError`；回调返回 `False` 是正常提前终止。

**新增后端三步（以 OpenAI 为例）**：① 新建 `dao/llm/providers/openai.py`，实现 `class OpenAIProvider(Provider)` 的三个抽象方法，网络/HTTP 失败抛 `ProviderError`；② 类上加 `@register_provider("openai")`；③ 在 `dao/llm/providers/__init__.py` 加一行 `from . import openai  # noqa: F401` 触发自注册（该文件已登记 ollama / openai / anthropic 三行）。业务侧只需把 `创建客户端` 的提供者名从 `ollama` 改为 `openai`，其余不变。

## 19.6 道语言「大模型」模块 API 参考

> 实现位于 `dao/stdlib/llm.py` 并注册到 `registry.py`。以下函数签名、参数顺序与字段键已与实现逐条核对确认；完整示例见 `示例/AI对话/接口层示例.道`。

标准库函数须用「从…导入」取用（直接 `导入 大模型` 会过滤掉函数，见现有示例说明）：`从 大模型 导入 消息, 创建客户端, 对话, 流式对话, 列出模型, 工具定义, 工具对话, 工具结果`（后三个为第三轮新增）。

注：Python 层 `ChatMessage.to_dict()` 返回英文键 `role`/`content`（供 Provider 请求体），桥接层按道语言习惯暴露中文字典；两套键的分工见 §19.3。

| 函数 | 参数 | 返回 |
|---|---|---|
| `消息` | `角色`, `内容` | 消息字典 `{"角色": ..., "内容": ...}` |
| `创建客户端` | `提供者`, `配置字典`（键即 provider 配置项：`host`/`model`/`timeout`） | Provider 客户端对象（对应 `create_provider`） |
| `对话` | `客户端`, `消息列表`, `选项字典`（`模型`/`温度`/`最大token` 或英文 `model`/`temperature`/`max_tokens`，**中文键优先**） | 响应字典 |
| `流式对话` | `客户端`, `消息列表`, `回调函数`, `选项字典` | 累积后的响应字典 |
| `列出模型` | `客户端` | 模型名文本列表 |
| `工具定义` | `名称`, `描述`?, `参数模式`?（1~3 参，第三轮新增） | OpenAI 风格 tool 字典 |
| `工具对话` | `客户端`, `消息列表`, `工具列表`, `回调函数`, `选项字典`（第三轮新增） | 中文键工具对话结果字典 |
| `工具结果` | `调用编号`, `内容`（第三轮新增） | `role="tool"` 消息字典 |

`对话` / `流式对话` 返回 `ChatResponse.to_dict()` 的中文键：`内容`/`模型`/`角色`/`思考`/`完成原因`/`用量`（`提示token`/`生成token`/`总token`，后端 extra 平铺进去）/ `成功`（值 `真`）/ `原始`。`流式对话` 的回调签名是 `函数(块)`，块字典来自 `StreamChunk.to_dict()`：`内容`/`思考`/`完成`——`完成` 只是「最后一块」的标志，**不是终止开关**；提前终止靠回调**返回 `假`**。`消息列表` 元素支持中文键 `角色`/`内容` 或英文键 `role`/`content`（`消息()` 生成中文键）。

**错误约定**：`对话` / `流式对话` / `列出模型` 捕获 `LLMError` 后统一返回 `{"成功": 假, "错误": "中文描述"}`，不抛异常栈（与现有 `对话.道` 的 `应答["成功"] == 假` 范式一致）。**例外**：`创建客户端` 在配置缺失/提供者未知时抛中文「运行时错误」（形如「创建大模型客户端失败：...」），不返回字典；需要兜底时应对其单独用 `尝试/捕获`。

第三轮新增的 `工具定义` / `工具对话` / `工具结果` 的完整签名、参数、返回与最小示例见《标准库API/大模型.md》，协议数据流与降级约定见 §19.10。其中 `工具对话` 固定 5 个参数、`选项字典` 支持「最大轮次」（正整数，默认 5），回调固定收 2 参（名称、参数字典）并返回结果文本。

```道
从 大模型 导入 消息, 创建客户端, 对话

定义 客户端 = 创建客户端("ollama", {"model": "gemma4:e4b"})
定义 历史 = [消息("system", "你是简洁的中文助手。"),
             消息("user", "用一句话介绍道语言。")]
定义 应答 = 对话(客户端, 历史, {"温度": 0.7})

如果 应答["成功"] == 真
    打印(应答["内容"])
    打印(`token：{应答["用量"]["总token"]}`)
否则
    打印(`调用失败：{应答["错误"]}`)
```

```道
从 大模型 导入 消息, 创建客户端, 流式对话

函数 收到(块)
    如果 长度(块["内容"]) > 0
        打印(块["内容"], 结尾="", 刷新=真)
    返回 真

定义 客户端 = 创建客户端("ollama", {})
定义 应答 = 流式对话(客户端, [消息("user", "讲个短故事")], 收到, {})
打印("")
```

## 19.8 测试与验收

**测试文件位置**（实际交付路径）：

- `tests/test_llm_ollama.py`（15 项）：Ollama 的 `chat` / `chat_stream` / `list_models`、thinking 与 usage 解析、回调提前终止、HTTP mock。
- `tests/test_llm_remote.py`（13 项）：OpenAI / Anthropic 的请求头与请求体拼装、SSE 流式解析、配置缺失与 HTTP 错误、模型列表，全部 HTTP mock，不打外网。
- `tests/test_stdlib/test_llm.py`（16 项）：5 个中文函数、中文键返回、`{"成功": 假, "错误": ...}` 约定、`创建客户端` 失败抛运行时错误、道语言端到端脚本。

## 19.10 工具调用协议层（2026-11-22，第三轮迭代）

> 本节为第三轮迭代新增，把 §19.4 预留的 `chat_with_tools` 扩展点补全为完整可用的 Function Calling / Tool Use 协议。共享契约见《示例/更夫/迭代规约-工具调用.md》§4／§5／§6／§8／§9；本节只描述**契约与数据流**，逐函数签名见《标准库API/大模型.md》。

### 19.10.1 新增的统一类型

- `ToolDefinition`（`types.py:93-114`）：`name`（工具名）、`description`（给模型看的说明）、`parameters`（英文键 JSON Schema）。`to_dict()` 返回 OpenAI 风格 tool 字典 `{"type":"function","function":{"name":...,"description":...,"parameters":...}}`。
- `ToolCall`（`types.py:117-127`）：`id`（调用编号）、`name`（工具名）、`arguments`（**已解析的参数字典**，不是 JSON 字符串）。`to_dict()` 返回中文键 `{"编号","名称","参数"}`。
- `ChatRequest.tools` / `ChatResponse.tool_calls` 从预留字段变为真正的数据通道；`ChatResponse.to_dict()` 新增 `工具调用` 键（无调用时为 `[]`）。

### 19.10.2 统一 tool_calls 结构（两层键约定）

| 层 | 结构 | 键语言 | 说明 |
|---|---|---|---|
| Provider（`ChatResponse.tool_calls`） | `[{"id": ..., "name": ..., "arguments": {...}}]` | 英文 | 各后端归一化后的统一规范；`arguments` 已解码为字典 |
| 道语言（`ChatResponse.to_dict()["工具调用"]`） | `[{"编号": ..., "名称": ..., "参数": {...}}]` | 中文 | `ToolCall.to_dict()` 产物，业务层直接消费 |
| 请求侧（`ChatRequest.tools`） | `[{"type":"function","function":{...}}]` | 英文 | `ToolDefinition.to_dict()` 产物，Provider 自行转后端格式 |

后端无 `id` 时（如早期 ollama）由 Provider 按位置生成 `call_0`、`call_1`……；`arguments` 为 JSON 字符串时由 Provider 用 `json.loads` 解码，解码失败当空字典并保留原始内容到 `raw`。

### 19.10.3 Provider 契约

`Provider.chat_with_tools(request: ChatRequest) -> ChatResponse` 保持非抽象，基类默认仍抛 `UnsupportedError`。三个 Provider 均已实现：

- **无 tools 时**：行为与 `chat(request)` 一致（内部委托 `chat`）。
- **有 tools 时**：把 `request.tools` 转成后端格式发起请求，响应中的工具调用归一化为 §19.10.2 的英文键结构填入 `ChatResponse.tool_calls`；`content` 为模型附带文本（可能为空串）；`usage` 正常填写；`finish_reason` 保留后端原值（如 `tool_calls`）。
- **失败处理**：Provider 层沿用既有约定，抛 `ProviderError` / `ConfigError`，不吞异常；道语言层的降级见 §19.10.6。

### 19.10.4 数据流

```text
道语言业务（示例/AI对话/工具调用示例.道 / 更夫 Worker）
  │  工具定义() → 工具列表；消息() → 消息列表
  ▼
stdlib「大模型」.工具对话（dao/stdlib/llm.py，InterpreterBuiltin，固定 5 参）
  │  构造 ChatRequest，填入 tools
  ▼
Provider.chat_with_tools（dao/llm/providers/{ollama,openai,anthropic}.py）
  │  后端请求：ollama /api/chat 的 tools 字段 ｜ OpenAI chat/completions 的 tools ｜ Anthropic messages 的 tools
  ▼
后端归一化 tool_calls → {"id","name","arguments"}
  │
  ├─ 有工具调用：逐个回调 工具函数(名称, 参数字典) → 结果文本
  │                 → 追加 role="assistant"(tool_calls) 与 role="tool"(tool_call_id) 消息
  │                 → 回到 工具对话，进入下一轮
  └─ 无工具调用：返回最终内容 + 工具调用记录 + 累计用量 + 轮次
```

多轮循环由 `工具对话` 内部完成；道语言只提供一个回调，不手工维护 `tool` 消息。需要手工控制的高级用法可用 `工具结果(调用编号, 内容)` 自行构造 `role="tool"` 消息。

### 19.10.5 道语言桥接三函数

| 函数 | 固定参数 | 要点 |
|---|---|---|
| `工具定义` | `名称`, `描述`, `参数模式` | `参数模式` 支持中文键 `{"属性":{...},"必填":[...]}` 或英文 JSON Schema；返回 tool 字典 |
| `工具对话` | `客户端`, `消息列表`, `工具列表`, `回调`, `选项字典` | 自动多轮；回调收 2 参（名称、参数字典）并返回结果文本；`选项字典` 支持「最大轮次」（正整数，默认 5）及 `模型`／`温度`／`最大token` |
| `工具结果` | `调用编号`, `内容` | 构造 `{"角色":"tool","内容":...,"调用编号":...}`，供手动模式 |

`工具对话` 返回中文键字典：成功含 `成功`／`内容`／`工具调用记录`／`用量`／`轮次`；失败含 `成功`(假)／`错误`／`工具调用记录`／`用量`／`轮次`（失败时**不含** `内容`）。`工具调用记录` 元素为 `{"名称","参数","结果"}`。详见《标准库API/大模型.md》。

### 19.10.6 降级与多轮上限

- **后端不支持**：基类或 Provider 抛 `UnsupportedError`（`LLMError` 子类），`工具对话` 捕获后返回 `{"成功": 假, "错误": ...}`，不抛异常栈。
- **调用失败**：网络／HTTP／配置错误（`ProviderError` / `ConfigError`）同样转成失败字典；已积累的 `工具调用记录`、`用量`、`轮次` 一并带回，便于排查。
- **回调失败**：工具回调自身抛异常时转成结果文本「工具执行失败：...」，不中断对话循环。
- **轮次上限**：`最大轮次` 默认 5 且必须为正整数，否则直接返回失败字典「最大轮次必须是正整数」；达到上限仍无最终答复时返回失败字典并保留全部记录，防止模型与工具互相触发导致死循环。
- **定位**：LLM 仍是**增强项而非依赖**——工具失败时业务可退回模板／规则路径，演示不中断。
