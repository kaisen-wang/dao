## 一、严重问题 (Critical)

### 1. `len()` 函数误用 — 运行时崩溃

> 状态：✅ 已修复（核对：`dao/interpreter/expressions.py:675,690` 为 `len(obj)` 单参数；运行验证索引越界正确抛 `索引错误 (长度 3)`，不再触发 `TypeError`）

**文件**: `源码/dao/interpreter/expressions.py:520, 535, 542`（早期快照行号）

```python
# 错误：len(obj, 0, 0, self.source) — len() 只接受1个参数
raise 索引错误(
    f"列表索引 {idx} 超出范围 (长度 {len(obj, 0, 0, self.source)})",
)
```

`len()` 被错误地传入了4个参数，这会在运行时直接抛出 `TypeError`，导致索引越界检查本身崩溃。同样的问题出现在 `eval_index_access` 方法的列表、字符串和类型错误分支中。

### 2. `type()` 函数误用 — 运行时崩溃

**文件**: `源码/dao/interpreter/statements.py:299`（早期快照行号）

```python
f"无法给类型 '{type(obj, 0, 0, self.source).__name__}' 设置索引",
```

`type()` 只接受1个参数，这里错误地传入了4个参数。

### 3. 三引号字符串未闭合检测失效

> 状态：✅ 已修复（核对：`dao/lexer/readers.py:154-155` 现为 `if self.current_char is None: raise 词法错误("未闭合的三引号字符串…")`；`tests/test_triple_quote.py`；运行验证确实抛错）

**文件**: `源码/dao/lexer/readers.py:154-156`（早期快照行号）

```python
if self.current_char is None and not (len(result) >= 0):
    pass
```

条件 `not (len(result) >= 0)` 永远为 `False`（因为 `len(result) >= 0` 恒为 `True`），所以这个 `if` 块永远不会执行。这意味着未闭合的三引号字符串不会报错，而是静默返回可能不完整的内容。

### 4. `DaoInstance.get_field` 无法区分 `None` 值和字段不存在

> 状态：✅ 已修复（核对：`dao/builtins/oop_types.py:125-148` 引入 `_MISSING` 哨兵并让 `get_field` 返回 `(value, found)` 元组；`dao/interpreter/expressions.py:364` 用 `result, found = obj.get_field(...)` 判定；运行验证 `None` 值返回 `(None, True)`、字段不存在返回 `(None, False)`）

**文件**: `源码/dao/builtins/oop_types.py:112-119`（早期快照行号）

```python
def get_field(self, name: str):
    if name in self.fields:
        return self.fields[name]
    method = self.klass.find_method(name)
    if method is not None:
        return BoundMethod(self, method)
    return None
```

当字段值为 `None` 时，`get_field` 返回 `None`，调用方无法区分"字段值为 None"和"字段不存在"。在 `expressions.py:253-261` 中：

```python
result = obj.get_field(expr.member)
if result is not None:
    return result
raise 名称错误(...)
```

如果字段值确实为 `None`，会错误地抛出 `名称错误`。

## 二、重要问题 (Major)

### 5. `MacroRegistry` 单例模式导致状态泄漏

> 状态：✅ 已修复（核对：`dao/macros/registry.py:45-52` 已是普通类、无 `__new__`/`_instance`；`dao/interpreter/core.py:57` 每个 `Interpreter` 独立 `MacroRegistry()`；`core.py:88-90` 用 `saved_macros` 保存再 `clear()`，不再跨实例互相影响）

**文件**: `源码/dao/macros/registry.py:48-55`（早期快照行号）

```python
class MacroRegistry:
    _instance = None
    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance._initialize()
        return cls._instance
```

`MacroRegistry` 使用单例模式，但 `Interpreter.execute()` 每次执行时都调用 `registry.clear()`（`源码/dao/interpreter/core.py:87-88`）。这意味着：
- 多个 Interpreter 实例共享同一个宏注册表
- 一个 Interpreter 执行 `clear()` 会影响其他 Interpreter
- 在并发场景下可能导致竞态条件

## 四、设计建议

### 21. 考虑使用访问者模式替代 Mixin + match

> 状态：📐 设计建议保留（核对：当前仍是混入类 `dao/interpreter/expressions.py:44` + `match expr`（`:108,734,789`）。属架构取舍，非缺陷，是否引入访问者模式可待 AST 节点规模进一步扩大再评估）

> 状态：📐 设计建议保留（已部分落实）（核对：`tests/test_dual_mode.py` 已建立双模式一致性测试套件，覆盖未定义变量、break/continue、闭包、内置函数、错误传播等约 36 例；本报告 #9/#10 相关的具体不一致均已修复。建议继续以该测试文件作为语义回归基线）

当前两种执行模式存在多处行为不一致（未定义变量处理、break/continue 支持等），建议建立统一的语义测试套件，确保两种模式行为一致。
